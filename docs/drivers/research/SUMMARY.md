# Three vendor dialects, one rollback-first generator

All three target platforms ship a documented, switch-side revert timer that maps directly onto the NetConfig push engine. On **Arista EOS** it is `configure session <name>` followed by `commit timer hh:mm:ss`. On **Junos** it is `configure private`, then `commit check`, then `commit confirmed N` (1–65,535 minutes, default 10). On **HPE Aruba AOS-CX** it is `checkpoint auto <1-60>` followed by `checkpoint auto confirm`. The arming commands are confirmed in official vendor documentation; the EOS confirm step is not (see below). The quality of the evidence behind everything else varies a lot by vendor. **AOS-CX is best documented**, because two complete official HPE PDF guides were read. **Junos ELS/SRX is confirmed mostly at the procedure level**, with exact `set` lines read for VLAN access ports, DHCP server and SRX NAT. **EOS is the weakest**: arista.com blocked most manual pages, so basic hostname, VLAN, switchport, SVI, OSPF and BGP syntax remains unverified this session. Netmiko 4.8.0, the version pinned in the project, drives all three over SSH. It has a commit helper only for Junos, no serial driver for any of the three, and no telnet driver for AOS-CX. The engine must also work around three Netmiko traps: AOS-CX sub-context prompts look like "not in config mode", Junos `exit_config_mode()` silently answers "yes" and discards uncommitted changes, and Arista has no commit helper at all. EIGRP is unsupported on every one of these platforms, and NAT exists only on SRX (and, depending on hardware, on EOS). The practical result is that all three drivers start as `experimental`. Verified syntax can go into golden files now, and every line marked U below must be proven on cEOS-lab, vJunos or the AOS-CX Simulator before a driver is promoted to `tested`.

**Status legend used in every table:** **V** = command text read verbatim from an official vendor source. **O** = official source confirms the procedure or behaviour, but the exact text came from a secondary source or a search extract. **C** = community or third-party source only. **U** = unverified: no source was retrieved this session. U syntax is candidate syntax from general vendor knowledge and must be lab-proven before use.

## Every platform has a revert timer, but each one confirms differently

**Arista EOS.** The documented syntax is `configure session [name] [abort | commit | description …]`, run from privileged EXEC. Inside the session, `commit timer hh:mm:ss` applies the staged changes and automatically rolls them back unless they are confirmed before the interval ends ([Arista Session Management Commands](https://www.arista.com/en/um-eos/eos-session-management-commands)). The same page gives three operational constraints. **Uncommitted sessions are lost on reboot and time out after 24 hours.** The number of pending sessions is capped by `service configuration session max completed <0-20> pending <1-20>`. Most importantly, **a commit replaces the running-config wholesale**, so changes someone else made after the session started are overwritten. The engine therefore has to serialise pushes per device.

The confirm step is the weakest link in the EOS evidence. Arista's page does not spell it out, and its own examples are inconsistent: after `commit timer` the prompt drops back to `switch#`, while after a plain `commit` it stays in session mode. A community walk-through fills the gap. Running `configure session <name> commit` from EXEC moves the session from `pendingCommitTimer` to `completed`, and an expired timer is logged as a config replace of `commitTimerCheckPointConfig` ([saidvandeklundert.net](https://saidvandeklundert.net/2019-10-15-arista_configure_sessions/)). The prompt shows only the **first six characters of the session name** ([Arista Configuration Sessions Overview](https://www.arista.com/en/um-eos/eos-configuration-sessions-overview)), so keep names short, for example `nc-<8hex>`.

**Junos.** Junos has the most complete official story. `commit check` "verif[ies] the syntax of the configuration, but do[es] not activate it". `commit confirmed <minutes>` accepts **1–65,535 minutes, default 10**, and rolls back automatically on timeout. "To confirm a commit, enter either a commit or commit check command." Since Junos 11.4, **`commit confirmed` is allowed in `[edit private]` mode** ([Juniper commit reference](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/commit.html)). The Junos XML protocol says confirmed commits are unavailable for a private copy ([Junos XML: Commit a Private Copy](https://www.juniper.net/documentation/us/en/software/junos/junos-xml-protocol/topics/task/junos-xml-protocol-configuration-committing-private-copy.html)), but that applies only to NETCONF, not the CLI that Netmiko drives. Private mode gives each user a separate candidate. If two users commit conflicting changes, "the first commit operation takes precedence". Exiting `configure exclusive` with "yes" discards uncommitted changes ([Juniper configure command](https://www.juniper.net/documentation/us/en/software/junos/cli/topics/topic-map/configure-command.html)). `rollback 0` discards pending candidate changes ([Juniper rollback reference](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/rollback.html)).

**AOS-CX.** AOS-CX works differently because there is **no staging area**: changes go live as they are typed. `checkpoint auto <1-60>` is run from the Manager (`#`) context and must come before the changes. If `checkpoint auto confirm` is not entered in time, "all configuration changes you made are discarded and the running configuration reverts" ([AOS-CX 10.10 Fundamentals Guide, pp.178–179](https://www.bhphotovideo.com/lit_files/1146748.pdf); same text in [techdocs 10.17](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.17/HTML/fundamentals_8400/Content/Chp_Cfg_FW_mgt/che-aut-mod.htm)). The guide prints the exact device output for both paths, which makes ideal golden fixtures:

- **Confirmed:** `Auto checkpoint mode expires in 20 minute(s)`, then `checkpoint AUTO20170801011154 created`.
- **Expired:** `WARNING: Restoring configuration. Do NOT add any new configuration.`, then `Restoration successful`.

A third-party blog gives the confirm command as `checkpoint confirm` ([Sikich](https://www.sikich.com/insight/how-to-use-aruba-cx-checkpoint-auto-commands/)). That contradicts the official guide and should be ignored. One older bug matters for the minimum firmware: **on 10.04 the revert did not fire if the admin disconnected first**. Aruba acknowledged it, and a reply reported it fixed in 10.06.0010 ([Aruba community](https://community.arubanetworks.com/discussion/aos-cx-8320-checkpoint-auto-minutes-failure-after-admin-disconnect)). The project's 10.10+ target range already clears that.

| Step | Arista EOS | Junos (EX ELS / SRX) | AOS-CX (6300/6100/Simulator) |
|---|---|---|---|
| Pre-change snapshot | Session is the snapshot (C) | Rollback files kept automatically (O) | `copy running-config checkpoint NCS_<job>`. Names: letters, digits, `_`, `-`; must not start with `CPC` (V) |
| Enter staging | `configure session nc-<id>` from EXEC (V) | `configure private` (O); `configure exclusive` as the alternative | None: arm the timer first, then `configure terminal` |
| Preview diff on device | `show session-config diffs` (C) | `show \| compare` (U) | None documented |
| Syntax check | None documented | `commit check` (V) | None |
| Arm revert timer | `commit timer 00:05:00` in session mode (V) | `commit confirmed 5` (V); in private mode since 11.4 (V) | `checkpoint auto 5` in Manager `#`, before the changes (V) |
| Confirm | `configure session nc-<id> commit` from EXEC (C) | `commit` or `commit check` (V) | `checkpoint auto confirm` (V) |
| Abort before arming | `configure session <name> abort`, or `abort` inside the session (V) | `rollback 0`, then exit (O) | Not applicable |
| Roll back now | Undocumented: test `abort` or `configure replace` (U) | `rollback 1` + `commit` (U) | `checkpoint rollback NCS_<job>` (V); whether it is allowed during auto mode is untested (U) |
| Save after confirm | `write memory` / `copy running-config startup-config` (U) | None needed: commit persists (O) | `write memory`, an alias of `copy running-config startup-config`, output `Success` (V) |
| Driver `rollback_strategy()` | `commit_timer` | `commit_confirmed` | `checkpoint_auto`, with a named checkpoint as the fallback |

## Netmiko 4.8.0 enters config mode on all three but commits only on Junos

Netmiko is the layer most likely to cause silent failures, so its behaviour was read straight from the pinned 4.8.0 source. **Device types** are `arista_eos`, `juniper_junos` and `aruba_aoscx`, each also accepted with an `_ssh` suffix. Telnet variants exist only for `arista_eos_telnet` and `juniper_junos_telnet`. The only serial strings are `cisco_ios_serial` and `furukawa_fitelnet_serial` ([ssh_dispatcher.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/ssh_dispatcher.py)). The project's console-bootstrap feature therefore needs a custom subclass, or a `generic`/`terminal_server` session, for all three vendors, and it cannot reach an AOS-CX lab console over telnet at all. Netmiko 4.8.0 is the current PyPI release ([PyPI netmiko](https://pypi.org/project/netmiko/)).

| Behaviour | `arista_eos` | `juniper_junos` | `aruba_aoscx` |
|---|---|---|---|
| Session preparation | `terminal width 511`, then disable paging ([arista.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/arista/arista.py)) | Enters `cli` if at a root shell; `set cli screen-width 511`, `set cli complete-on-space off`, `set cli screen-length 0` ([juniper.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/juniper/juniper.py)) | `no page`; no width set; `default_enter="\r"` ([aruba_aoscx.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/aruba/aruba_aoscx.py)) |
| Default config entry | `configure terminal` | `configure` | `configure term` (must be fully spelled, because the CLI auto-completes on space) |
| Config-mode detection | `")#" in output` | `"]"` (from `[edit]`); deliberately not `#` | Literal `"(config)#"` |
| Exit | `end` (inherited from Cisco) ([cisco_base_connection.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/cisco_base_connection.py)) | `exit configuration-mode`; answers **`yes`** to "Exit with uncommitted changes" | `end` (inherited) |
| `commit()` | None: raises `AttributeError` ([base_connection.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/base_connection.py)) | `commit(confirm, confirm_delay, check, comment, and_quit, read_timeout=120)`; success markers listed below | None |
| `save_config()` | `copy running-config startup-config` | Raises `NotImplementedError` | `copy running-config startup-config` |
| Custom session entry | `config_mode("configure session nc-<id>")` works from EXEC; does nothing if already in `(config)#` | `config_mode("configure private")` works; if refused, raises `ReadTimeout` instead of a clear error | Not applicable |

Three hazards come out of this source reading, and the push engine has to own each one.

1. **AOS-CX config-mode detection fails in sub-contexts.** The check looks for the literal `(config)#`, so inside `switch(config-if)#` Netmiko believes it is not in config mode. As a result, `exit_config_mode()` silently does nothing and `config_mode()` re-sends `configure term`. Every AOS-CX block should therefore end with an explicit `end`, or the engine should pass `check_string=")#"`.
2. **Junos exit discards work.** `exit_config_mode()` and `cleanup()` both answer "yes" to the uncommitted-changes prompt, which in private mode throws the candidate away without any error. Every `send_config_set` call must pass `exit_config_mode=False` until after the commit. Juniper's own older docs disagree on whether that prompt even appears ([Juniper 13.1 entering/exiting config mode](https://juniper.net/documentation/en_US/junos13.1/topics/task/configuration/junos-cli-configuration-mode-entering-exiting.html)), and the private-mode wording ("Discard uncommitted changes?") is unverified. If the wording differs, Netmiko waits for `>` and times out.
3. **Arista has no commit or abort helper.** The engine must send `commit timer`, `configure session … commit` and `… abort` itself, using `send_command(..., expect_string=...)`. Whether `end` inside a session commits it, leaves it pending or prompts is **unresolved** and has to be tested on cEOS.

Generic `send_config_set` reads each command's echo and then the prompt. It checks `error_pattern` against the *accumulated* output and has a 15-second `read_timeout`. Any command matching `^banner .*$` turns echo verification off for the whole batch ([base_connection.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/base_connection.py)). Sending **one command per call**, with banners in a call of their own, gives exact "stopped at command X" attribution on all three platforms.

The Junos `commit()` helper decides success only by looking for a marker string in the output:

| Command | Marker Netmiko expects |
|---|---|
| `commit` | `commit complete` |
| `commit check` | `configuration check succeeds` |
| `commit confirmed` | `commit confirmed will be automatically rolled back in` |

If the marker is missing, it raises `ValueError` with the full output. It refuses a `comment` containing `"`, and its 120-second default timeout may be too short for a slow vJunos ([juniper.py](https://github.com/ktbyers/netmiko/blob/develop/netmiko/juniper/juniper.py)).

## Layer-2 syntax is documented for AOS-CX and Junos ELS but not for EOS

AOS-CX Layer-2 syntax is fully verified, and it has one trap the generator must encode. **`vlan trunk native N` automatically runs `vlan trunk allowed all`**, so the explicit allowed list must always come after the native command ([C6100 CLI Guide p.1315](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf); [techdocs 10.15 native VLAN](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.15/HTML/l2_bridging_6300-6400/Content/Chp_vlans/asi-nat-vla-id-tru-int.htm)). There is no `switchport mode`: applying `vlan access` or `vlan trunk` decides the port type. VLANs can only go on non-routed ports, and "routing is disabled on all interfaces" by default on the 6300 ([F1010 p.85](https://www.bhphotovideo.com/lit_files/1146748.pdf)). A community report says the Simulator image defaults ports to *routed* ([Airheads](https://airheads.hpe.com/discussion/aruba-cx-on-eve-ng-routing-between-vlan)), so the generator should always emit `no routing` before `vlan access`/`vlan trunk`, which is harmless when it matches the default.

Junos ELS replaced pre-ELS `port-mode` with `interface-mode` and moved the native VLAN to the physical interface ([Getting Started with ELS](https://www.juniper.net/documentation/en_US/junos13.2/topics/task/configuration/getting-started-els.html)). The native VLAN must also be a member of the trunk, or untagged frames are dropped ([Native VLAN, ELS](https://www.juniper.net/documentation/en_US/junos13.2/topics/task/configuration/bridging-native-vlan-id-ex-series-cli-els.html)).

On EOS, every basic switchport line is unverified. The one adjacent official hint is that a "protect mode" for port security exists on newer releases ([Arista TOI index](https://www.arista.com/ko/support/toi/tag/toi?start=700)).

| Feature | Arista EOS | Junos ELS (EX, vJunos-switch) | AOS-CX |
|---|---|---|---|
| Hostname | `hostname NAME` (U) | `set system host-name NAME` (U) | `hostname NAME`: 1–32 characters, first a letter or digit (V, [F1010 p.333](https://www.bhphotovideo.com/lit_files/1146748.pdf)) |
| Domain | `dns domain NAME`; `ip domain-name` may be an alias (U) | `set system domain-name NAME` (U) | `ip dns domain-name NAME [vrf V]`; ignored if `ip dns domain-list` is set (V, [F1010 p.244](https://www.bhphotovideo.com/lit_files/1146748.pdf)) |
| Create VLAN | `vlan N`, then `name X` (U) | `set vlans NAME vlan-id N` (C, [open-exam-prep](https://open-exam-prep.com/study-guides/jncis-ent/vlans-inter-vlan-routing/irb-configuration-packet-walk); matches the official procedure O, [Juniper ELS L2](https://www.juniper.net/documentation/en_US/junos/topics/task/configuration/bridging-vlans-ex-series-cli-els.html)) | `vlan N`, then `name X`: 1–32 characters of letters, digits, `_`, `-`; names must be unique (V, [C6100 p.1299](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)) |
| Access port | `interface EthernetN`, `switchport mode access`, `switchport access vlan N` (U) | `set interfaces IF unit 0 family ethernet-switching interface-mode access` and `… vlan members N` (V, [Juniper OpenConfig VLAN mapping](https://www.juniper.net/documentation/us/en/software/junos/open-config/topics/concept/openconfig-vlan-mapping.html)) | `interface 1/1/N`, `no routing`, `vlan access N` (V, [C6100 p.1313](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)) |
| Trunk mode | `switchport mode trunk` (U) | `… interface-mode trunk` (O) | Implicit when `vlan trunk …` is applied (V) |

| Edge / portfast | `spanning-tree portfast` (U) | `set protocols rstp interface IF edge` (O, [Juniper RSTP example](https://www.juniper.net/documentation/en_US/junos/topics/example/stp-rstp-qfx-series.html)) | `spanning-tree port-type admin-edge` (V, [C6100 p.707](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)) |
| Port security | `switchport port-security …`; protect mode depends on platform (U) | `accept-source-mac mac-address …` (V); `switch-options … interface-mac-limit` hierarchy (U) | `port-access port-security enable`, then `client-limit N` (1–32 on 6100) (V, [C6100 pp.928–929](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)); 6300 (U) |

One Junos-specific consequence reaches into the safety layer. A unit that carries `family ethernet-switching` cannot also carry `family inet`. Converting a port from switched to routed therefore needs `delete interfaces IF unit 0 family ethernet-switching`, and `delete` is on the CLAUDE.md denylist. The Junos driver needs an **OS-specific denylist** that blocks a bare `delete` (which wipes the whole candidate) and destructive targets, while allowing scoped deletes the generator itself emits.

## Layer-3 and services coverage splits sharply by platform and model

The most important per-platform facts for the capability matrix are these.

**EOS DHCP server.** It is Kea-based and has existed since **EOS 4.22.1** ([Arista TOI dhcp-server](https://www.arista.com/en/support/toi/tag/dhcp-server)). EOS **silently disables** a subnet whose range falls outside its prefix, and it also disables overlapping subnets, instead of returning a CLI error ([EOS DHCP overview](https://www.arista.com/en/um-eos/eos-dhcp-overview)). Backend validation must catch these cases, and `check()` must read `show dhcp server` for "disabled" reasons.

**EOS NAT.** NAT is configured per L3 interface and has no inside/outside marking ([EOS Data Plane Security](https://www.arista.com/en/um-eos/eos-data-plane-security)). Arista's own sources conflict on overload support: a 7050CX4 TOI says "NAPT is not supported in masquerade or overload mode" ([Arista TOI](https://www.arista.com/ko/support/toi/tag/dcs-7050cx4)). An advisory also describes an ACL bypass with dynamic NAT on the 720XP up to 4.24.9 ([Security Advisory 0078](https://www.arista.com/zh/support/advisories-notices/security-advisory/15862-security-advisory-0078)).

**Junos.** NAT is SRX-only. "No source NAT pool is required for source NAT using an egress interface", but a trust→untrust security policy is ([Juniper Source NAT](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/nat-source.html)). The SRX DHCP server is JDHCP only from 15.1X49-D60/17.3R1 ([Juniper DHCP Server Configuration](https://www.juniper.net/documentation/us/en/software/junos/dhcp/topics/topic-map/dhcp-server-configuration.html)).

**AOS-CX by model.** The coverage gap is between models. The **6000/6100 10.10 CLI guide has no DHCP-server, OSPF or BGP commands** ([C6100](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)), and HPE's routing guide states "OSPFv2 is not supported on the 6000 and 6100 Switch Series" ([techdocs 10.14 IP Routing PDF](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.14/PDF/ip_route_4100i-6000-6100-6200.pdf)).

| EIGRP | Unsupported (no EIGRP chapter in the manual index; inferred) | Unsupported (no `protocols eigrp` hierarchy; inferred) | Unsupported (zero matches in either guide) |

EIGRP is "unsupported" on all three, but no vendor states this explicitly. It rests on the absence of any EIGRP documentation and on EIGRP being a Cisco-originated protocol. That is still a firm basis for the driver to raise "EIGRP is not supported on <OS>" instead of skipping the feature silently.

## Users, saving, error strings and show commands close the loop

Each vendor needs a different way to handle the local admin user.

**Junos.** `plain-text-password` prompts interactively to enter and confirm the password. Putting a plaintext value into `encrypted-password` makes the account impossible to log into ([Juniper User Accounts](https://www.juniper.net/documentation/us/en/software/junos/user-access/topics/topic-map/junos-os-user-accounts.html)). The generator should therefore pre-compute a `$6$` SHA-512-crypt hash and send `encrypted-password "<hash>"`. Python's `crypt` module is not available on Windows, so the backend needs its own implementation; the untracked `backend/app/security/shacrypt.py` appears to be that work.

**AOS-CX.** `password plaintext` "is visible as cleartext when entered" and "command history does show the password as cleartext" ([C6100 p.1285](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)). The masker must add `password plaintext`, `password ciphertext` and `authorized-key` to its patterns. AOS-CX usernames must be lowercase, at most 32 characters, and cannot be `admin` or `root`. A Security Guide example uses `TestUser1` ([AOS-CX 10.14 Security Guide mirror](https://netz.schulon.org/fw/CX/Dokumentation/10.14/security_6200-6300-6400.pdf)), which contradicts that rule, so validate to the stricter rule. AOS-CX has **no enable secret**: administrators land directly at `#`.

On AOS-CX it must reject the chosen delimiter and `?`, and Aruba Central notes that `#` breaks banners in templates ([Configuring AOS-CX Using Templates](https://arubanetworking.hpe.com/techdocs/fedramp/webhelp/content/nms/aos-cx/get-started/prov-tmplt-cx.htm)).

**Error strings.** Only AOS-CX has officially documented ones: `Invalid input: <token>` and `% Command incomplete.` ([F1010](https://www.bhphotovideo.com/lit_files/1146748.pdf)). The REST error table also groups "Ambiguous command" with those two ([techdocs 10.13 REST error codes](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.13/HTML/rest_v10-0x/Content/Chp_AnyCLI/err-codes.htm)). The EOS set comes from a third-party driver template: `% Invalid input`, `% Ambiguous command`, `% Unrecognized command`, `% Incomplete command` ([rneter arista.rs](https://docs.rs/crate/rneter/0.4.1/source/src/templates/network/arista.rs)). The usual candidates (`syntax error`, `unknown command`, `missing argument`, `error: configuration check-out failed`, `error: commit failed`) are unverified, so the most reliable Junos signal is a missing Netmiko success marker. Treat `warning: statement not found` as non-fatal. Freeze every string in golden tests from real lab output.

## Recommended capability matrix and support labels

Splitting Junos into two `os_id`s is justified. SRX needs security zones and policies before any routed traffic flows, and NAT exists only on SRX ([Juniper Source NAT](https://www.juniper.net/documentation/us/en/software/junos/nat/topics/topic-map/nat-source.html)). AOS-CX needs **per-model** capability flags rather than per-OS ones, because the 6100 lacks DHCP server, OSPF and BGP ([C6100](https://download.axilogi.com/HPE/Manual/HPE_6000_a_6100_MCG.pdf)).

In the table below, "doc" means the syntax is documented (V/O) but the feature stays `experimental` until it passes a lab test. "exp" means the syntax is unverified (U/C) and is labelled experimental in the UI. "no" means the driver must raise "not supported on <OS>".

The safety layer needs vendor-specific additions to match. On AOS-CX, add these to the denylist: `erase checkpoint …` and `erase startup-config` ([F1010 p.195](https://www.bhphotovideo.com/lit_files/1146748.pdf)); `checkpoint rollback` when it comes from the custom-commands box (only the engine may roll back); `no user`; and `no ssh server vrf <management VRF>`. On Junos, block these OS-specific items:

- a bare `delete`
- `load override` and `load factory-default`
- `request system zeroize` and `request system reboot`
- `rollback` from custom commands
- `delete`/`deactivate` on the management interface

On EOS, add `configure replace` and banner `EOF` injection to the existing checks.

## Conclusion

The three safety nets look equivalent on a slide but protect different things. EOS stages changes but commits by **replacing the whole running-config**, so its risk is concurrent edits rather than typos. Junos is the only platform that **checks syntax before anything goes live** and treats commit as save. AOS-CX applies every line live, and its `checkpoint auto` window is capped at **60 minutes**. That means the NetConfig preview is the only "dry run" an AOS-CX engineer ever gets, so the backend's validation carries more weight on Aruba than on the other two. The engine should also treat Netmiko as a transport, not a mode manager: on all three platforms its default config entry, exit and save helpers either do nothing, do the wrong thing, or silently discard work in exactly the rollback paths this project depends on.

The evidence gaps reverse the obvious order for lab work. EOS has the most unverified syntax yet the friendliest free lab image (cEOS-lab), so it should be proven first: capture real `show` output with `| json`, settle what `end` does inside a session and how a `commitTimer` session is confirmed, and convert its U rows into golden files. AOS-CX can move to `tested` fastest, because nearly everything is documented and only the DHCP `default-router`/`lease` syntax and rollback during auto mode remain open. Junos sits in between: its lab work is mainly capturing the exact error, refusal and exit-prompt strings that the error detection depends on.
